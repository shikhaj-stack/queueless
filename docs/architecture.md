# Queueless Bhopal — Backend Architecture

Companion to `api-contracts.md`. That document defines the wire contract; this one
defines how the backend is put together behind it.

Status: Phase 0, design only. No code exists yet.

---

## 1. Stack

| Layer | Choice |
| --- | --- |
| API | Next.js App Router route handlers under `app/api` |
| Language | TypeScript, strict |
| Database | Supabase PostgreSQL |
| Realtime | Supabase Realtime on `tokens` and `queue_events` |
| Validation | Zod at every trust boundary |
| AI runtime | Claude API for citizen-facing assistant and service search |
| Service engineering | Claude Code pipelines, offline and admin-triggered |
| Deploy | Vercel |

The Next.js application itself is scaffolded and owned by the frontend teammate. The
backend adds directories to that application; it does not create a parallel project.

## 2. Layering

Requests flow in one direction only.

```
route handler        parse, authorise, shape the response
      |
      v
service layer        business rules, transactions, cross-entity logic
      |
      v
repository layer     one module per table group, the only place Supabase is called
      |
      v
Supabase PostgreSQL
```

Rules:

- Route handlers contain no SQL and no business rules. They validate with Zod, call one
  service function, and map the result through the shared response helper.
- Services never touch the Supabase client directly. Repositories never make
  authorisation decisions.
- Where a service would be a bare passthrough to a single repository call, the route
  calls the repository directly rather than adding a file that does nothing.
- Anything that must be atomic lives in a Postgres function, not in TypeScript.

## 4. Two Supabase clients, never mixed

- `lib/db/server.ts` uses `SUPABASE_SERVICE_ROLE_KEY`. It bypasses RLS and is imported
  only from server code. Every write in the system goes through it.
- `lib/db/browser.ts` uses `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Its only job is the
  Realtime subscription on `tokens` and `queue_events`.

The service-role key is never prefixed `NEXT_PUBLIC_` and never imported into a client
component. If it reaches the browser the entire security model is void.

## 5. Authorization

Demo identity, real enforcement.

`lib/auth/session.ts` exposes:

- `getSession()` — resolves the current demo user, or null.
- `requireUser()` — throws `UNAUTHENTICATED` when there is no session.
- `requireRole('staff', 'admin')` — throws `FORBIDDEN` when the role does not match.
- `requireOwnerOr('staff', 'admin')` — for records a citizen may read only when they
  own them.

The role is read from `public.users.role`, keyed by the session user id. It is not
trusted from the request body, a header, or a client-supplied field.

Every staff and admin route calls a guard as its first statement. Frontend role checks
are cosmetic and are never the enforcement point.

## 6. Queue engine

The parts that must not race are in SQL.

`issue_token(queue_id, user_id)`

```sql
update queues
   set last_issued_token = last_issued_token + 1
 where id = p_queue_id
returning last_issued_token;
```

Atomic under concurrency, strictly ordered, no advisory locks, deterministic enough to
rehearse in front of judges.

The one-active-token rule is a database constraint, not an application check:

```sql
create unique index one_active_token
    on tokens (queue_id, user_id)
 where status in ('waiting', 'called');
```

An application-level check would have a time-of-check/time-of-use window; the index
does not. A violation surfaces as `409 CONFLICT`.

Position is derived on read, never stored:

```
position = count(tokens where queue_id = $1
                   and status = 'waiting'
                   and token_number < mine) + 1
```

Storing position would mean rewriting every waiting row on each dequeue.

Rolling average: on `complete`, the served duration folds into
`queues.average_service_minutes`. Estimated wait is `people_ahead x average`.

Every state change writes a `queue_events` row. That table plus `tokens` is what the
frontend subscribes to.

`reset` clears tokens for a queue and returns counters to their starting values so a
demo run can be repeated.

## 7. Application status engine

Applications never advance automatically from queue events. Every change is explicit,
staff- or admin-driven, and recorded.

`application_status_events` is the timeline. It is append-only: rows are inserted,
never updated or deleted. `applications.status` is a denormalised pointer to the latest
event, kept in the same transaction as the insert so the two cannot drift.

The allowed transition map lives in one place in `lib/services/application-engine.ts`
and is enforced there, not at the call site:

| From | Allowed next |
| --- | --- |
| `submitted` | `under_review`, `rejected` |
| `under_review` | `processing`, `approved`, `rejected` |
| `processing` | `approved`, `rejected`, `completed` |
| `approved` | `completed` |
| `rejected` | none |
| `completed` | none |

Creating an application seeds the timeline with a `submitted` event, so the timeline is
never empty. Every accepted transition also writes an `audit_log` row.

Reference numbers are simulated, prefixed `QLB-SIM-`, and labelled `simulated: true` in
every response that carries them.

## 8. Validation

Zod schemas live in `lib/validation`, one file per domain, and are the single source of
truth for request shape. Every route parses body, query, and route parameters through a
schema before anything else runs — including fields the frontend already validates.

Parsed output is the typed value the rest of the handler uses. No handler reads
`request.json()` directly.

## 9. Error handling

`lib/api/respond.ts` owns the mapping from error code to HTTP status and produces the
two envelope shapes from `api-contracts.md`. Handlers throw typed errors; the helper
converts them. No handler builds a `NextResponse` by hand.

Internal failures are logged server-side with detail and returned to the client as a
generic `INTERNAL` message. Database errors, stack traces, and upstream payloads never
reach the response body.

## 10. Database tables

Core, from Handoff Section 4:

`users`, `departments`, `locations`, `services`, `service_requirements`,
`service_steps`, `visual_guides`, `visual_guide_steps`, `applications`, `queues`,
`tokens`, `queue_events`, `verification_reports`

Added in this phase:

- `application_status_events` — persistent application timeline. New table; see
  `api-contracts.md` Section 8 for why the handoff schema needed it.
- `service_flags` — citizen-reported discrepancies, feeding the Verification Agent.
- `audit_log` — every admin mutation to a published service and every application
  status change.

Not implemented this phase: `notifications`, `saved_services`.

## 11. Migrations

Numbered, forward-only, applied in order. Planned sequence:

```
001_extensions.sql        pgcrypto
002_core.sql              users, departments, locations
003_services.sql          services, requirements, steps, visual guides
004_applications.sql      applications, application_status_events
005_queue.sql             queues, tokens, queue_events
006_verification.sql      verification_reports, service_flags
007_audit.sql             audit_log
008_constraints.sql       indexes, partial unique index, CHECK constraints
009_functions.sql         issue_token, call_next, complete_token
010_rls.sql               row level security policies
011_realtime.sql          publication for tokens and queue_events
```

Enumerations are `CHECK` constraints on text columns rather than Postgres enum types.
Adding a value to a `CHECK` is a one-line migration; altering an enum type is not.

## 12. Security posture

- Secrets only in `.env.local`, never in the repository. `.env.example` carries keys
  with empty values and nothing else.
- Service-role key is server-only.
- All writes go through the service role; the anon key has `SELECT` on `tokens` and
  `queue_events` and nothing more.
- Every staff and admin route is guarded server-side.
- All input validated server-side regardless of client validation.
- Published service definitions are mutable only through the admin publish flow.
- Simulated data is labelled as simulated in every response that carries it.
- Official source-backed facts are kept separate from AI-generated explanation text.
